    Backends and GPUs¶

    Every backend runs the same compiled host program (C). They differ in how the parallel loops inside it are executed.

    backend Parallel loops run on Notes
    "auto" the best multi-core strategy found default; same as "multicore"
    "c" the calling thread no threads at all; also compiles without parallel loop overhead
    "threads" Parakeet's persistent thread pool POSIX; fork-safe; no extra runtime library
    "gcd" Grand Central Dispatch macOS
    "openmp" the compiler's OpenMP runtime needs libgomp/libomp (macOS: brew install libomp)
    "metal" / "mps" the Apple GPU pip install "parakeet[metal]==1.0.0"
    "cuda" an NVIDIA GPU pip install "parakeet[cuda12]==1.0.0" (CuPy)
    "python" — runs the original function uncompiled 
    parakeet.available_backends()
# {'python': 'ok', 'c': 'ok', 'threads': 'ok', 'gcd': 'ok', 'openmp': 'ok', 'metal': 'ok',
#  'cuda': 'unavailable: the CUDA backend needs CuPy, which is not installed. Install ...'}

    A backend that cannot work fails when you select it, with a message saying what is missing and how to install it — not later with a linker error.

    Multi-core¶

    Array expressions, map/allpairs/imap, comprehensions, parfor and reductions over recognised associative operations are split into chunks that run on parakeet.config.num_threads threads (default: all cores). Only the outermost data-parallel operation is parallelised; anything nested inside it runs sequentially within each thread.

    Small loops are not worth a thread hand-off: loops with a cheap body run on the calling thread unless they have at least 2 * config.parallel_grain iterations (default 8192 per chunk). Loops whose body contains loops of its own are always split.

    Compiled functions release the GIL and are safe to call from several Python threads at once. With multiprocessing, prefer the spawn start method when using "openmp" or "gcd" (those runtimes do not survive fork); the default thread pool does.

    Apple GPUs (Metal)¶

    @jit(backend="metal")
def blur_energy(img):
  return (img[1:-1, 1:-1] * 4 - img[:-2, 1:-1] - img[2:, 1:-1] - img[1:-1, :-2] - img[1:-1, 2:]) ** 2

    Each eligible parallel loop is also compiled to a Metal compute kernel; the host program hands loops of at least config.device_threshold iterations (default 32768) to the GPU and runs smaller ones on the CPU.

    Apple GPUs have no float64

    Metal does not support double precision. A loop that touches float64 data runs on the CPU thread pool instead, and Parakeet emits a FallbackWarning saying so. Pass float32 arrays and np.float32 scalars to stay on the GPU (a Python float argument is a double; x * 2.0 with a literal is fine).

    Other reasons a loop stays on the CPU: it allocates temporary arrays per iteration, or it uses a function Metal lacks (lgamma, erfc). The warning always names the reason. Control this with config.device_fallback: "warn" (default), "silent", or "error" to refuse instead.

    Runtime errors inside kernels (out-of-bounds indices, failed assertions) are reported as normal Python exceptions.

    NVIDIA GPUs (CUDA)¶

    @jit(backend="cuda")
def distances(X, C):
  return parakeet.allpairs(lambda a, b: np.sum((a - b) ** 2), X, C)

    Kernels are compiled at run time by CuPy's RawKernel (NVRTC), so only the NVIDIA driver and a CuPy wheel matching your CUDA version are needed. All dtypes including float64 are supported. The same per-loop fallback rules apply.

    Validation status

    CI has no NVIDIA hardware, so there the CUDA code generator runs against a simulator (PARAKEET_CUDA_SIMULATE=1) that compiles the generated kernels as C++ and executes their thread grid on the CPU.

    The 1.0 release comparison ran on a physical NVIDIA A10 with strict device dispatch. Earlier checks on an A100 (Google Colab, CuPy with CUDA 13, Python 3.13) and Tesla T4 covered the whole test suite with every parallel loop forced onto the GPU (688 tests, including the tiled products, the gradient tests and arrays kept on the device between loops), the examples and the benchmarks all passed. That check is run on demand, not by CI:

    pip install runplz google-colab-cli
runplz colab tools/colab_job.py          # T4; PK_COLAB_GPU=A100 for others

    To push your own test suite through a GPU set PARAKEET_TEST_BACKENDS=cuda (the backends used by parakeet.testing.expect and check) and PARAKEET_DEVICE_THRESHOLD=1 (so small arrays go to the device too).

    What about TPUs?¶

    No. A TPU only runs programs compiled by XLA, which wants whole-array operations with static shapes; Parakeet generates scalar loops in C-like kernel languages. Parakeet's CPU backends do work on a Colab TPU host (24 x86 cores), which is all PK_COLAB_TPU=v5e1 runplz colab tools/colab_job.py checks.

    How data moves¶

    Arrays belong to the host, but within one call they stay on the device.

    • The first GPU loop that uses an array puts it on the device. A buffer the host allocated and has not written to yet (the output of the loop, usually) is created there directly: nothing is copied. On Metal, arrays allocated by compiled code are shared with the GPU without copying at all.
    • Later loops find the array already there. What a loop wrote stays on the device; it is not copied back after every loop.
    • Host code that reads or writes array memory itself (an explicit Python loop, a loop that fell back to the CPU, a call into the BLAS) first asks for everything the device has changed. So does the end of the call.
    • A temporary that is freed before anyone on the host looked at it is never copied back.

    A chain of array operations on a GPU therefore costs one upload of its inputs and one download of its result, however many loops it has. Mixing GPU loops with scalar host loops over the same arrays works, and gives the same answers, but pays for a download and an upload each time the two alternate.

    Which loops go to the device. A loop is sent when its number of elements times the estimated inner iterations per element reaches config.device_threshold, and it has at least 1024 elements. A loop over 5,000 rows that each need a 10,000-step inner loop goes; a loop over 20,000 cheap elements stays on the CPU, where the launch would cost more than the work; so does a loop over 32 features however long each one's scan is, because a device runs one (slow) thread per element and 32 of them are no match for a few CPU cores.

    Use parakeet.to_device(x, backend="cuda") or backend="metal" to reuse resident array inputs across calls. Pass the resulting device arrays to a compiled function and call parakeet.to_host(result) when Python needs the data. Operations which run on the host can still require transfers.
